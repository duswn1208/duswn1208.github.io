자세히 보기

타 팀 서비스의 중복 발송 CS로 전사 대응 지침이 내려왔습니다. 우리 팀은 발송·과금 단계에 이미 Redis 락이 있어 실제 중복은 없었지만, 지침에 따라 같은 수신자에게 같은 내용을 1시간 안에 다시 보내려 하면 사용자에게 먼저 안내하는 기능이 필요했습니다. 5개 서비스에 각각 구현하면 방식이 갈라질 것 같아 공통 라이브러리를 제안했고, 방향은 제가 정해 팀에 공유한 뒤 단독 구현했습니다.

  • 메커니즘은 공통, 정책은 서비스 — 라이브러리는 해시 생성·Redis SETNX + TTL 60분 등록·허용 상태 관리만 맡고, 검사 대상 발송 수단·단건 제외·허용 분기는 서비스에 남김. 서비스마다 정책이 달라 공통에 넣으면 옵션과 분기가 늘어난다고 판단. 서비스 DTO는 어댑터로 변환해 넘겨 라이브러리가 의존하지 않음
  • 수신자 해시: 설계 → 측정 → 결정 — 수신자 최대 11만 건이라 앞·중간·끝 샘플링을 설계. 로컬 측정에서 11만 건 기준 전체 해시 82ms, 샘플링 6~15ms로 절대 차이는 수십 ms. 중간 수정을 놓칠 수 있어 오탐 없는 전체 해시를 택하고 샘플링은 설정값으로 남김
  • Redis 선택과 fail-open — 조회가 빠르고 TTL 관리가 쉬우며 DB 접근이 없음. 막는 장치가 아닌 안내 장치라, Redis 장애·키 유실에도 발송은 정상 진행 (중요한 건 발송이지 중복 체크가 아님)
  • 요청 단위 / 오늘 하루 허용 — 팝업 “확인” 후 재발송 한 건은 요청 플래그로, “오늘 하루 열지 않기”는 사용자 단위로 Redis에 당일 23:59:59까지 저장. 기기 간 일괄 적용 필요 여부는 사업팀에 확인
✓ 5개 서비스 적용, 로직 개발·테스트는 1회분 + 서비스별 e2e

Redis Sentinel Failover 후 Lettuce 커넥션 불능 장애현 직장
Redis SentinelLettuceRedissonTomcat

네트워크 단절 후 Sentinel이 failover했지만 Lettuce를 쓰는 세션·캐시가 새 마스터로 붙지 못해 흰 화면이 노출된 장애. 장애 당일 개발 서버에서 재현까지 마치고 원인을 찾았습니다.

  • kill -9로는 재현이 안 돼 kill -STOP으로 “살아 있지만 응답 못 하는” 상태를 만들어 재현
  • 타임아웃·풀 옵션 조정은 직접 실험으로 기각, autoReconnect가 죽은 마스터에 재연결하며 명령이 쌓이는 것이 원인
  • 리뷰에서 autoReconnect(false)의 위험이 제기돼 번복, 최종은 commandTimeout 2s + validateConnection(true)
✓ 최종 설정으로 kill -STOP 환경에서 자동 복구 재검증✓ 운영 반영

한계 — 운영의 실제 failover로 검증된 적은 없고, 최종 설정은 재현 환경과 리뷰로 수렴한 값입니다.

자세히 보기

가상화 서버 네트워크 단절로 Redis 마스터가 내려가 Sentinel이 failover했지만, Lettuce를 쓰는 세션·캐시가 새 마스터로 붙지 못해 흰 화면이 노출됐습니다. 첫날 혼자 재현해 원인을 찾았고, 이후 팀과 설정을 여러 번 검증·번복하며 최종안으로 수렴했습니다. 재현 테스트는 마지막까지 제가 이어서 진행했습니다.

  • 재현 — 운영과 같은 방화벽·IP 설정의 개발 환경에서 kill -9는 소켓이 닫혀 재현되지 않았고, 인프라팀 협조로 네트워크를 차단하면 재현됨. 혼자 빠르게 반복하려고 kill -STOP으로 “살아 있지만 응답 못 하는” 상태를 만들어 같은 증상을 재현
  • 직접 실험으로 기각 — 타임아웃·재시도·readmode 조정은 Redisson만 개선하고 Lettuce는 그대로. 풀 옵션은 리소스만 안정화시켰을 뿐 죽은 마스터에 매달린 커넥션은 그대로
  • 원인과 1차 해결 — autoReconnect가 죽은 마스터 IP로 재연결을 반복하며 명령이 큐에 쌓임. autoReconnect(false) + 타임아웃 + validateConnection 조합(각각 단독은 실패)으로 복구. 서비스는 풀이 아닌 공유 커넥션이라 풀 대여 시점 검증이 적용되지 않아 validateConnection이 필요
  • 번복 — 리뷰에서 autoReconnect(false)의 위험(순단에도 연결이 영구히 죽음, 재연결마다 핸드셰이크 비용)이 제기됨. 기본값으로 되돌리고 끊긴 동안 명령을 쌓지 않는 REJECT_COMMANDS를 시도했고, keepAlive는 이번 장애와 직접 연관이 없어 제거
  • 최종 구성 — commandTimeout 2s + validateConnection(true). 비로그인 폴백 페이지는 제가 구현했고, 서킷브레이커와 캐시 대체값 처리는 팀원이 보완
✓ 최종 설정으로 kill -STOP 환경에서 자동 복구 재검증✓ 운영 반영, 이후 같은 상황 없음

한계 — 운영의 실제 failover로 검증된 적은 없습니다. 최종 설정은 “최적값”이 아니라 재현 환경과 리뷰로 수렴한 값입니다. 회고 — 기본값을 의심해 원인을 찾았지만 반대 극단(false)에도 비용이 있다는 걸 리뷰에서 배웠습니다. 기본값과 그 반대를 둘 다 비교하고 결정해야 합니다.

같은 캠페인에 편집·발송·취소가 동시에 몰려도, 같은 요청이 재시도돼도 발송건이 한 번만 만들어지게 하는 설계. 발송 요청 접수 영역을 설계·구현했습니다. 설계 중 본문 편집과 발송의 경합으로 중복·낡은 본문 발송이 가능하고, 수정 후 재발송 시 이전 멱등키가 재사용돼 정상 요청이 무시될 수 있음을 발견했습니다.

  • 캠페인 행 직렬화 — 트랜잭션 진입 직후 FOR UPDATE로 잠그고 본발송 중복·테스트 발송 한도·진행 중 테스트 판정을 모두 잠금 아래에서 수행. 한도를 잠금 아래에서 세므로 동시 요청이 넘지 못함

  • 서로 다른 두 장치 — 멱등키(선확인 → 잠금 아래 재확인 → 유니크 위반 후 재조회)는 같은 요청의 재시도를, 캠페인 잠금과 “일반 캠페인 본발송 1건” 규칙은 키가 다른 중복 요청을 방어. 프론트는 요청 내용·본문 저장 세대가 바뀌면 새 키를 발급

운영 CS: 후불 미납금이 차감되지 않고 선불 충전금으로 충전됨. 같은 쿼리가 접속 환경에 따라 다른 날짜로 해석됐고, 2025년에는 우연히 동작하다가 2026년이 되며 드러난 잠복 버그였습니다.

  • 가설 좁히기 — 개발·운영 DB 툴에서 쿼리가 모두 정상 조회돼 쿼리 자체는 문제없다고 보고 파라미터인 날짜를 의심. 운영 로그에서 종료일이 2026-01-25가 아닌 2025-01-26으로 찍힌 것을 확인
  • 모순에서 얻은 단서 — 날짜 형식 문제로 보였지만 DB 툴에서는 정상이라 DBA에게 확인을 요청, 애플리케이션 세션과 DB 툴 세션의 NLS_DATE_FORMAT 차이를 확인
  • 원인 — 날짜에 일수를 더하고 || ' 23:59:59'를 이어 붙여 TO_DATE로 재파싱하는 구조라 세션 포맷에 따라 종료일이 달라짐. 종료일이 25일이라 2025년에는 연도와 일이 같아 어느 포맷이든 결과가 같았고, 2026년에 앱 세션에서만 0건
  • 두 겹의 수정 — DBA에게 세션 NLS 통일을 요청하되 코드도 문자열 변환 후 BETWEEN 비교를 날짜 직접 비교로 변경: REG_DT >= TRUNC(SYSDATE,'MM') AND REG_DT < TRUNC(SYSDATE,'MM') + 25
✓ 동일 패턴 9곳 + 같은 팀 다른 서비스 9곳 직접 수정

한계 — 영향 건수는 이후 사용 이력 때문에 정확히 추출하지 못했습니다. 회고 — “DB 툴에서는 되는데 애플리케이션에서만 안 된다”는 환경 의존의 신호라서, 설정 통일과 별개로 환경에 영향받지 않는 코드로 바꿨습니다.

  • 원인과 수정 — 센서 상태 확인(10초 주기)과 시간당 수집 개수 계산이 한 프로그램에서 함께 돌아, 한 시간에 한 번이면 되는 계산이 10초마다 실행. 모든 센서를 갱신하던 것을 활성 센서만 갱신하도록 바꾸고, 수집 개수 계산은 cron(매시간)으로 도는 일회성 프로그램으로 분리
