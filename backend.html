  • 캠페인 개념 제안·설계 — 조건이 맞을 때마다 자동 발송되는 트리거 발송, 여러 번의 테스트발송, 자동저장까지 묶기 위해 캠페인 – 발송건 – 수신 대상의 3단 구조로 설계하고, 사용자 상태와 발송 처리 상태를 분리
  • 발송 요청 검증과 큐 역할 분리 — 서비스 정책 검증은 큐 적재 전에 처리해 즉시 안내하고, 큐 이후는 수신자별 분배만 빠르게 처리
  • 테스트발송 중 본문 수정 차단 — 테스트 완료 전까지 수정·본발송을 막아 의도치 않은 본문 발송 방지

자세히 보기
  • 왜 캠페인이 필요했나 — 처음에는 기존 문자처럼 발송건만으로 구성하는 방법도 생각했습니다. 하지만 메일은 사용자가 만든 발송건이 트리거로 계속 발송되고, 발송 결과에서는 트리거를 여러 발송건이 아니라 하나로 보여줘야 했습니다. 한 캠페인에서 테스트발송을 여러 번 할 수 있어야 했고, 발송 페이지에 들어가자마자 제목과 입력값이 자동저장돼 발송하지 않을 내용도 저장되므로, 발송건과는 다른 상위 개념으로 묶어야 했습니다.
  • 구조와 상태 분리 — 캠페인은 유형(웹발송, 트리거)과 사용자 액션에 따른 상태를 갖습니다. 예를 들어 발송 요청 전이면 임시저장, 요청이 접수되면 진행중, 발송이 끝나면 완료입니다. 발송건의 상태는 순수하게 발송에 필요한 값으로만 구성해, 사용자가 보는 상태와 발송 처리 상태를 나눴습니다.
    캠페인 · 유형(웹발송/트리거) · 사용자 액션 기준 상태 · 발송일 └ 발송건 · 테스트발송 / 본발송 / 트리거 발화분 · 발송 상태 └ 수신 대상
  • 설계 중 바꾼 결정: 승인 상태의 위치 — 처음에는 모든 발송건마다 어드민 확인이 필요하다고 해서 승인을 발송건 기준으로 만들었습니다. 하지만 사용자 입장에서는 캠페인이 하나의 발송이고, 트리거는 승인받지 못하면 아예 실행되지 않아야 했기 때문에, 설계 중간에 승인 상태를 캠페인으로 옮겼습니다.
  • 캠페인의 발송일 — 원래 발송건에 있는 발송일을 캠페인에도 두었습니다. 진행 중인 캠페인은 발송일이 현재 이후면 예약, 이전이면 진행중으로 보여주고, 트리거는 활성화 시작일을 여기에 둔 뒤 발송될 때마다 갱신해 마지막 발송일로 씁니다. 그래서 발송 결과 화면은 유형과 관계없이 발송일 하나로 보여줄 수 있습니다.
  • 큐 적재 전 검증 — 메일 HTML의 안전성과 템플릿 구조, 발신 주소 상태, 입력한 변수의 유효성, 글자 수, 승인 대상 여부 같은 서비스 정책을 확인합니다. 서비스 정책이 들어간 검증이라 큐에 넣기 전에 처리하고, 실패하면 즉시 안내해 사용자가 수정 후 다시 보낼 수 있게 했습니다.
  • 큐 이후의 역할 — 큐 이후는 게이트웨이에 전달하기 전에 수신자별로 펼쳐 주는 역할만 빠르게 하도록 정책 판단을 앞단에 모았습니다.
  • 테스트발송 중 본문 수정 차단 — 발송건이 본문을 복사하지 않고 참조하는 구조라, 테스트발송 도중 본문을 고치면 수정본이 의도치 않게 나갈 수 있었습니다. 캠페인에 엮인 테스트발송건이 진행 중이면 본문 수정과 본발송 요청을 거부하고, 사용자가 실제 수신을 확인할 수 있도록 테스트발송이 성공한 뒤에 수정할 수 있게 했습니다.
  • 승인 흐름 — 어드민 승인 없이는 발송할 수 없는 회원의 메일은 어드민이 본문의 스팸성을 확인해 승인하고, 승인 시점에 대기 중이던 발송 요청을 큐에 넣습니다. 너무 늦게 승인된 요청은 본문의 의미가 사라지므로(예: 주말에 보내려던 메일이 평일에 바로 발송) 발송하지 않고 취소합니다.
  • 예약 발송 취소 — 예약 건은 큐 이후 DB 폴링으로 시간이 맞으면 요청되므로, 취소 시 캠페인과 발송건 상태를 취소로 바꿔 처리합니다.

  • 부정결제 방어 — 결제 금액을 서버에서만 확정해 PG로 전달하는 구조로 변경, 불일치 시 사용자 정지
  • 카카오 연동·API 명세 제안 — 여러 프론트 개발자가 쓰는 발신프로필 API 문서화를 제안·작성
✓ 결제 금액 서버 확정 구조 적용
자세히 보기
  • 가결제·종결 처리란 — 문자는 건당 과금인데, 통신사 결과를 받은 뒤 차감하면 그 사이 잔액이 부족해질 수 있습니다. 그래서 발송 시도 시점에 성공을 가정한 금액을 사용자가 쓰지 못하게 잡아두고(가결제), 통신사 결과를 받으면 성공분만 실제 차감하고 실패분은 돌려주며 잔액·통계를 정리합니다(종결 처리). 예를 들어 10건을 보내 7건이 성공하면 10건분을 잡아뒀다가 7건분만 차감합니다.
  • 모바일쿠폰·팩스로 확장 — 문자에 있던 이 구조를 바탕으로 모바일쿠폰과 팩스의 종결 처리를 개발했습니다. 건당/장수별 과금, 국내·국제 기준 금액 등 도메인별 규칙을 적용했고, 백엔드 단독 개발 건이라 테스트 코드로 검증했습니다.
  • 놓친 예외와 바뀐 습관 — 팩스는 장 단위로 과금하는데, 수신번호가 휴대폰번호면 여러 장을 보내도 1장만 성공으로 처리되는 예외가 있었습니다. 이 케이스를 설계에서 놓쳐 운영 후 금전 손실이 생겼고, 이후로는 설계 단계에서 도메인의 예외 케이스를 먼저 하나씩 확인하는 습관이 생겼습니다.
  • 부정결제 방어 — 클라이언트에서 결제 금액을 조작하는 경우에 대비해 프론트에서 금액을 조정하지 못하게 막고, PG로 보내는 결제 금액은 백엔드가 정한 값만 쓰도록 바꿨습니다. 실결제 금액과의 정합성도 확인해, 맞지 않으면 사용자를 즉시 정지·로그아웃하고 알림을 보내도록 했습니다.
  • 카카오 연동·API 명세 제안 — 보통 한 사람이 한 도메인의 프론트·백엔드를 함께 맡았는데, 카카오 연동에서는 처음으로 나눠서 진행했습니다. 협업할 때마다 메신저로 확인하게 되고, 제가 만든 발신프로필 API를 여러 프론트 개발자가 써야 해서 문서화를 제안하고 직접 작성했습니다.

Redis Sentinel Failover 후 Lettuce 커넥션 불능 장애현 직장 · 2026.04
Redis SentinelLettuceRedissonTomcat

네트워크 단절 후 Sentinel이 failover했지만 Lettuce를 쓰는 세션·캐시가 새 마스터로 붙지 못해 일정 시간 흰 화면이 노출된 장애입니다.

  • 원인 — 응답하지 못하는 마스터 상황을 직접 재현해, autoReconnect가 죽은 마스터에 재연결하며 명령이 쌓이는 것을 확인
  • 해결 — autoReconnect(false)는 리뷰에서 끊긴 연결이 자동 복구되지 않는 위험이 지적돼 철회, commandTimeout 2s + validateConnection(true)로 자동 복구
  • 재발 방지 — 팀이 맡은 유사 서비스 5개 전체의 같은 설정 점검
✓ kill -STOP 환경에서 자동 복구 재검증 후 운영 반영✓ 유사 서비스 5개 점검
자세히 보기
  • 재현 — 운영과 같은 설정의 개발 환경에서 kill -9는 소켓이 닫혀 재현되지 않았고, 인프라팀 협조로 네트워크를 차단하면 재현됐습니다. 혼자 빠르게 반복하려고 kill -STOP으로 “살아 있지만 응답 못 하는” 상태를 만들어 같은 증상을 재현했습니다.
  • 직접 실험으로 기각 — 타임아웃·재시도·readmode 조정은 Redisson만 개선하고 Lettuce는 그대로였습니다. 풀 옵션은 리소스만 안정시켰을 뿐 죽은 마스터에 매달린 커넥션은 그대로였습니다.
  • 원인과 1차 해결 — autoReconnect가 죽은 마스터 IP로 재연결을 반복하며 명령이 큐에 쌓였습니다. 서비스는 풀이 아닌 공유 커넥션이라 풀 대여 시점 검증이 적용되지 않아 validateConnection이 필요했습니다.
  • 번복 — 리뷰에서 autoReconnect(false)로 두면 순간 끊김에도 연결이 자동으로 복구되지 않는다는 위험이 제기돼, 기본값으로 되돌리고 다른 조합을 검증했습니다.
  • 최종 구성 — commandTimeout 2s + validateConnection(true). 비로그인 폴백 페이지는 제가 구현했고, 서킷브레이커와 캐시 대체값 처리는 팀원이 보완했습니다.
  • 재발 방지 — 팀이 맡은 비슷한 성격의 발송 서비스 5개에 같은 설정이 있는지 확인해 함께 반영했습니다.

한계 — 운영의 실제 failover로 검증된 적은 없고, 최종 설정은 재현 환경과 리뷰로 수렴한 값입니다. 회고 — 기본값을 의심해 원인을 찾았지만, 반대 극단(false)에도 비용이 있다는 걸 리뷰에서 배웠습니다.

Oracle 세션 설정에 따라 결과가 달라지던 날짜 조건 버그현 직장 · 2026.01
OracleSQL

정산 금액이 잘못 처리되던 운영 CS입니다. 2025년에는 우연히 정상 동작하다 2026년이 되며 드러난 잠복 버그였습니다.

  • 원인 — 운영 로그에서 종료일의 연도가 앞당겨 찍힌 것을 단서로, 서버 세션은 직접 조회할 수 없어 DBA에게 확인을 요청해 앱 세션과 DB 툴 세션의 NLS_DATE_FORMAT 차이를 규명
  • 해결 — 문자열 변환 비교를 날짜 직접 비교로 변경, 세션 설정 통일 요청
  • 재발 방지 — 같은 패턴 18곳을 다른 서비스까지 직접 수정
✓ 본 서비스 9곳 + 같은 팀 다른 서비스 9곳 직접 수정
자세히 보기
  • 가설 좁히기 — 개발·운영 DB 툴에서 쿼리가 모두 정상 조회돼 쿼리 자체는 문제없다고 보고 파라미터인 날짜를 의심했습니다. 운영 로그에서 종료일의 연도가 1년 앞당겨 찍힌 것을 확인했습니다.
  • DBA 확인 — DB 툴 세션은 직접 조회할 수 있지만 서버에서 붙는 세션은 조회할 수 없어 DBA에게 확인을 요청했고, 두 세션의 NLS_DATE_FORMAT이 다르다는 것을 확인했습니다.
  • 원인 — 날짜에 일수를 더하고 || ' 23:59:59'를 이어 붙여 TO_DATE로 다시 파싱하는 구조라 세션 포맷에 따라 종료일이 달라졌습니다. 2025년에는 연도와 일자 값이 우연히 맞아떨어져 어느 포맷이든 결과가 같았고, 2026년에 앱 세션에서만 0건이 나왔습니다.
  • 두 겹의 수정 — DBA에게 세션 설정 통일을 요청하고, 코드도 문자열로 변환해 다시 파싱하던 비교를 TRUNC 기준의 날짜 직접 비교로 바꿨습니다.

한계 — 영향 건수는 이후 사용 이력 때문에 정확히 추출하지 못했습니다. 회고 — “DB 툴에서는 되는데 애플리케이션에서만 안 된다”는 환경 의존의 신호라, 설정 통일과 별개로 환경에 영향받지 않는 코드로 바꿨습니다.

  • 좁혀 간 순서 — NCP 모니터링 → top(mongod가 대부분) → mongotop(컬렉션별 읽기 지연) → 인덱스 유무별 쿼리 시간 비교
  • 가설 기각과 격리 — 인덱스가 있는 쿼리는 0ms인데도 지연이 컸고 사용자 쿼리가 없는데도 부하가 계속돼, 데이터를 저장하는 프로그램 두 개를 번갈아 꺼 보며 원인 프로그램을 특정(mongod CPU 193% → 약 절반)
  • 원인과 수정 — 센서 상태 확인(10초 주기)과 시간당 수집 개수 계산이 한 프로그램에서 함께 돌아, 한 시간에 한 번이면 되는 계산이 10초마다 실행. 활성 센서만 갱신하도록 바꾸고, 수집 개수 계산은 cron(매시간)으로 도는 일회성 프로그램으로 분리
